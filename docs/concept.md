# 設計メモ — KAIROS SUPPORT

## 1. 何を解こうとしているか

KAIROS は「できること」が多い代わりに、設定が**宣言的・スクリプト的**になりがちです。

- レイヤー合成が自由すぎて、どこを触ると本線が変わるのか分かりにくい
- マクロがコマンド列で、書ける人と書けない人が分かれる
- 入力・マルチビュー・パネル・音声が別々の設定画面に散っている

ATEM が広く使われている理由は機能の多さではなく、
**「押せば画が変わる」が最初の 5 分で分かること**にあります。
そこを KAIROS に持ち込むのがこのアプリの狙いです。

## 2. UI の骨格

```
┌──────────────────────────────────────────────┐
│ 上部レール：接続先 / 基準信号 / TC / ON AIR   │
├────┬─────────────────────────────────────────┤
│ 左 │                                          │
│ レ │   作業エリア（画面ごとに入れ替わる）      │
│ ー │                                          │
│ ル │                                          │
├────┴─────────────────────────────────────────┤
│ コントロールサーフェス（常時表示）            │
│  PGM バス / PVW バス / NEXT / T バー / AUTO   │
└──────────────────────────────────────────────┘
```

**コントロールサーフェスを常時表示にしたのが最大の判断**です。
設定画面に潜っても本線が見えている＝物理パネルの前に座っている状態を再現します。

## 3. KAIROS の概念 ↔ ATEM の操作感

| KAIROS | このアプリでの見せ方 |
| --- | --- |
| Scene（シーン） | 画面上部の「シーン」チップ。ATEM の M/E に相当する単位として扱う |
| Layer（レイヤー） | レイヤースタック。上が前面。BG / KEY / DVE をバッジで区別 |
| Layer のソース A / B | PGM / PVW バス。押した瞬間に source が入る |
| Layer トランジション | NEXT（BKGD / KEY1 / KEY2）＋ T バー＋ AUTO / CUT |
| Snapshot | スナップショットのボタン群。マクロからも呼べる |
| Macro | **ブロックエディタ**。並べた結果をコマンドに変換 |
| AUX | Macro の「AUX 出力を切り替える」ブロック、Audio の出力ルーティング |

## 4. マクロエディタの考え方

ブロック 1 つ = KAIROS コマンド 1〜2 行。

| ブロック | 生成される行（サンプル） |
| --- | --- |
| ソースを切り替える | `SCENES.MainPGM.Layers.Background  sourceB = INPUTS.IP2` |
| トランジション実行 | `… effect = MIX  duration = 30` ＋ `… TransitionAuto()` |
| キーを切り替える | `SCENES.MainPGM.Layers.Key1  opacity = 1.0  duration = 18` |
| スナップショット呼出 | `SCENES.MainPGM.Snapshots.SNAP1  Recall()` |
| AUX 出力を切り替える | `AUX.3  source = SCENES.MainPGM.Program` |
| 待機 | `WAIT  frames = 60` |
| 次の操作を待つ | `PAUSE` |
| GPI 出力 | `GPIO.OUT2  Pulse(200)` |
| 音声フェード | `AUDIO.CH9  gain = -60.0  duration = 60` |

ポイントは **生成コマンドを隠さない**ことです。
隠すと「何をされたか分からない道具」になり、現場では信用されません。
書けない人はブロックだけ見て、書ける人は右の欄で確認できる、という二層構造にしています。

> 上記のコマンド表記は UI 検討用のサンプルです。
> 実装前に対象 Core のファームウェア仕様で確定させる必要があります。

## 5. 配色・書体

| 役割 | 値 | 理由 |
| --- | --- | --- |
| 筐体 | `#0C0F13` / `#141922` / `#232B37` | 青みを含むグラファイト。ラック機材の面 |
| アクセント | アンバー `#FFB020` | 選択・フォーカス・アプリの状態のみ。信号 LED の色 |
| PGM | `#FF2D46` | 意味色。装飾には使わない |
| PVW | `#38D46A` | 同上 |
| AUX / IP | `#4A9EFF` | ルーティングと IP 系の種別 |
| パネル見出し | Barlow Condensed（大文字・字間広め） | ハードウェアのシルク印刷 |
| 本文 | Barlow ＋ Noto Sans JP | 欧文と和文の高さを揃える |
| 数値・コマンド | JetBrains Mono | 桁を揃える（タイムコード、IP、生成コマンド） |

ダーク一択にしています。副調のモニター前で使う道具なので、
明るい面を作らないこと自体が要件です。

## 6. 次に決めること

1. **接続方式** — KAIROS Core への制御は何を使うか（制御ポート / REST / AMP）
2. **書き込み単位** — 差分書き込みが可能か、プロジェクト全体の入れ替えか
3. **同時操作** — KAIROS Creator や Control パネルと同時に触ったときの整合
4. **対象機種** — Core 100 / 200、Control の型番でキー数と挙動が変わる
5. **オフライン編集** — 実機なしで作って現場で流し込む運用を前提にするか
